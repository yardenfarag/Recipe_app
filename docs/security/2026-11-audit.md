# Security audit: user data leaks (PIN-54)

**Date:** 2026-11-02
**Audience:** Anyone working on the Pinch backend, the Edge Functions or the app.
**Scope:** The seven areas in PIN-54: database, Edge Functions, storage, share links, client bundle, third parties and account deletion.

We checked the live database (grants, RLS policies, `SECURITY DEFINER` functions, storage policies, Supabase advisors) and read the code. We did not send any requests to production.

## Summary

| # | Severity | Area | Finding | Status |
|---|---|---|---|---|

| E1 | **High** | Functions | SSRF: URL checks look only at the literal hostname, redirects are followed, and second-hop URLs (`og:image`, video) are fetched with no check. | Open |

Nothing we found lets one signed-in user read or change another user's rows. The database checks are listed under "What we checked and found clean".

## Database

**What we checked and found clean**

- Every table in `public` has RLS enabled.
- Every user-owned table's policies are scoped to `auth.uid()`.
- Tables with no policies (`guest_*`, `recipe_shares`, `recipe_share_claims`) are reachable only through the service role.
- `profiles`: users can update only `email`, `avatar_url`, `token_pack_notify_at`, `kitchen` and `contribute_to_hub`, so they can't set `is_admin` or change their balance.
- The admin RPCs (`admin_delete_user`, `admin_grant_recipe_credits`, `admin_credit_health`) check `profiles.is_admin` inside the function.
- Credit RPCs are locked to `service_role` (0043).

**H1 (Medium): users can publish anything to the hub.**

- Cause: `bump_recipe_card_on_recipe_insert` publishes any `recipes` insert with `extraction_status = 'full'`, and any signed-in user can insert a `recipes` row directly through the REST API.
- Exploit: insert a recipe for a popular URL before anyone extracts it, with a spam title and a tracking `image_url`. That content becomes the public card for every later visitor.
- Fix: publish to the hub only from the service role (the extraction function), not from a client-writable trigger. Alternatively, mark rows written by Edge Functions and publish only those.

**Low**

- anon has column `INSERT`/`UPDATE` grants on every `profiles` column, including `is_admin` and `token_balance`. RLS blocks those writes today, but the grants should be revoked as defense in depth.
- `ensure_user_profile(p_user_id)` can be called by anon with any id. It reveals whether that user exists (only if the attacker already knows the UUID) and fills in the user's profile.
- Trigger functions show up as RPCs. They can't be called that way, but they should still be revoked.
- `recipe_card_public_slug` has a mutable `search_path`. `pg_trgm` is installed in `public`.
- Leaked password protection (HaveIBeenPwned) is off in Auth settings.

## Storage

**S1 (High), fixed: anyone could list both buckets.**

- Cause: the SELECT policies `bucket_id = 'avatars'` (0002) and `bucket_id = 'recipe-thumbnails'` (0006) applied to every role.
- Exploit: with only the anon key, an attacker could:
  - list `recipe-thumbnails/photo/` and download every Snap photo (cookbook pages, handwritten family recipes, photos of dishes and kitchens), including from recipes never shared. Production held 17 such photos.
  - list `avatars` (path `<user id>-<timestamp>.<ext>`) to collect every user id.
- Fix: drop both policies. Public buckets serve files by URL without one, and the app never lists. Avatars keep an owner-only SELECT for upsert.

**S2 (Medium), fixed: no limits on avatar writes.**

- Users could upload any file of any size under any name, including names that start with another user's id.
- Fix:
  - Uploads must start with `<auth.uid()>-`.
  - Avatars are capped at 5 MB, and thumbnails at 10 MB.
  - Both buckets accept only image types, without SVG.
  - The settings screen now takes the extension from the picker's mime type, because web gives a `data:` URI.

**S3 (Medium): Snap photos are never deleted.**

- `persistUploadedPhoto` writes `photo/<random uuid>.<ext>` with no owner and no link back to the recipe.
- Neither recipe deletion nor delete-account can find these files.
- Fix:
  - Store the object path on the recipe.
  - Delete the file when the recipe or the account is deleted.
  - Consider moving user photos to a private bucket with signed URLs.

**Low:** `persistUploadedPhoto` trusts the mime type the client declares. Check the magic bytes.

## Edge Functions

**Clean:** delete-account, recipe-share, suggest-substitution and translate-recipe.

- They take the user from the JWT and ignore ids in the request body.
- No function returns the service-role key.
- Credit refund and finalize RPCs filter on `user_id`, so another user's reservation id can't be used.

**E1 (High): SSRF.**

- `_shared/webRecipe.ts` checks only the literal hostname. `isPrivateIp` misses IPv4-mapped IPv6, 100.64/10, and hostnames that resolve to private IPs.
- `fetchHtml` follows redirects.
- These fetch page-supplied URLs with no check at all:
  - `persistThumbnail.ts` (`fetchImageAsBase64`)
  - `videoInput.ts`
- Error messages reveal whether a target answered, so the function can be used as a port scanner.
- Fix: one `safeFetch` helper that resolves DNS, rejects private, loopback, link-local and CGNAT ranges, follows redirects manually and re-checks every hop. Use it for every fetch of a user-influenced URL.

**E2–E5 (Medium): billing and cost.** See the summary table.

- E2 and E3 come from code reading and need a reproduction before we fix them.
- E5 may be intended during the sandbox rollout (`docs/RECIPE_CREDITS_ROLLOUT.md`). Decide whether production should ignore `SANDBOX` events.

**Low**

- `extract-recipe` sends raw `FetchError` messages to the client, including `|| url=…, status=…, originalError=…`. They contain no secrets. Map errors to fixed messages.
- `revenuecat-webhook` compares the secret with `!==`. Use a constant-time compare. It already refuses requests when the secret is unset.
- `videoInput.ts` buffers the whole body when there is no `content-length`. Stream it with a byte cap.
- `backfill-thumbnails` lets anonymous callers spend YouTube API quota.
- `invent-recipe` trusts `already_gated` from the client. The credit is still charged.

## Share links (`/s/<token>`)

**Clean**

- Tokens are 18 random bytes (144 bits).
- Tokens are not logged or tracked.
- The snapshot contains no user id, email or avatar.
- The worker escapes all HTML and JSON-LD.
- The only redirect goes to `pinch://s/<token>`.
- Claims are idempotent and only ever create a row for the caller.

**L1 (Medium): links can't be revoked.**

- `revoked_at` exists, but nothing sets it.
- When the sharer deletes the recipe, `source_recipe_id` becomes NULL and the snapshot, including any Snap photo, stays public.
- Sharing is off in the app (`RECIPE_SHARE_ENABLED = false`), but the function and the worker still serve existing tokens.
- Fix: before turning sharing on, add a `revoke` action, revoke shares when the source recipe is deleted, and add a revoke button in the app.

**Low:** add `Referrer-Policy: no-referrer` to the share page, and tell users that a shared photo becomes public.

## Client bundle

**Clean**

- No secrets are in git or in the web export.
- The only key shipped is the publishable Supabase key.
- `EXPO_PUBLIC_ADMIN_EMAILS` only hides UI. The server trusts `profiles.is_admin` alone.

**B1 (Medium):** `.gitignore` covers `.env` and `.env*.local` but not `.env.production`. Ignore `.env*` and add `!.env.example`.

**Low**

- Admin emails are compiled into the public web bundle. Drop the email fallback.
- The `EXPO_PUBLIC_GEMINI_API_KEY` mentions in old docs should be removed so nobody brings back a client-side LLM key.

## Third parties and personal data

**Clean**

- OpenRouter gets prompts and content only, with no user id or email, and `data_collection: 'deny'`.
- ScrapeCreators gets only the post URL.
- RevenueCat gets only the Supabase user id.
- No JWT or service key is sent to any third party.
- Function logs hold ids, hosts and lengths, not request bodies or auth headers.

**P1 (Medium):** the anon policy on `product_events` allows any `guest_install_id` and any `properties` JSON, with no limit on size or rate. Cap `properties`, allow-list keys per event, or move inserts behind a rate-limited RPC.

**Low**

- **R1:** no retention anywhere. `feedback`, `support_tickets`, `product_events` (install id + country), `ai_usage_events` and the guest tables keep data forever. Add a pg_cron purge.
- Up to 800 characters of the OpenRouter error body end up in `ai_usage_events.error_message`. Store the status and error type only.
- The privacy policy should say that photos and typed text go to an LLM provider, and that we store country with analytics events.

## Account deletion

**Removed:** the auth user cascades to `profiles` and from there to:

- recipes, collections, shopping list, translations
- the ledger, usage and reservation tables
- purchase grants
- shares and claims

delete-account also removes avatars named `<uid>-*`.

**D1 (Medium): left behind**

- `support_tickets`: email and message
- `feedback`: message, contact email, device fields
- `product_events` and `ai_usage_events`: install id, country, metadata
- `purchase_webhook_failures.app_user_id`
- the guest tables
- every Snap photo (S3)

Fix: delete-account should delete or anonymize these rows and remove photo files once S3 records which files belong to whom.

**Info:** cascading `purchase_credit_grants` deletes purchase records we may need for store disputes. Decide whether to keep them anonymized.

## Regression tests

- `supabase/tests/storage_privacy.sql`: anon and other users can't list either bucket, avatar uploads are held to the user's own prefix, and both buckets cap size and refuse SVG.
- The `supabase/tests` suite does not run in CI yet. PIN-35 adds that job and the per-table RLS allow/deny tests.
